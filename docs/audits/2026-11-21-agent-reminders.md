# 从 personal agent 安排一次本机提醒

基线为 `e34455c`。本轮只给外部 agent 开放创建一次相对时间提醒的能力。用户继续在个人助手面板中管理已保存的提醒。[接入与撤销](../../README.md#agent-reminders) · [接口契约](../architecture.md#agent-reminders)

## 从一句话到 Windows 通知

在 Windows x64、Node 24.12.0、dsh 0.2.2-rc.1 上，使用隔离 profile、临时 Runtime 数据库和真实 stdio MCP 插件。向 dsh 的原生对话循环提交「半小时后提醒我休息」。一个本地确定性测试 Provider 用现有规则解析实际收到的文字，返回工具调用，用该条用户消息的 ID 标记意图。宿主执行工具，再把创建回执交回同一轮对话。此测试不使用个人配置或在线模型。

| 观察点 | 结果 |
| --- | --- |
| 首次受理与重试 | 正文为「休息」，首次到期时间恰为受理时钟加 1,800,000 毫秒。同一请求再调用得到相同的请求 ID、提醒 ID 和时间，SQLite 中只有 1 条提醒。 |
| 撤销与宿主退出 | 撤销后，同一 MCP 进程的新建请求被拒。dsh 随后退出，已保存的提醒仍为待投递。 |
| 恢复与投递 | 将测试 Runtime 墙钟推进至原定时间前 1 秒，重启并确认未提前投递。到点后调度器调用真实 Windows 通知接口 1 次，状态为 `accepted`、尝试次数为 1、`seenAt` 为空。再重启后仍只有这一次投递。 |

只推进隔离进程的墙钟，未修改操作系统时钟或等待真实半小时。已验证 Windows 受理，用户是否看到横幅、任意第三方模型是否会自主选中该工具以及其他平台的通知投递均未验证。系统接口返回与 SQLite 最终记账之间若发生崩溃，恢复仍沿用原投递 ID，具体外部显示遵循平台行为。

从已构建的源码复跑 `node scripts/acceptance-dsh-reminder.mjs` **会产生一条真实系统通知**。还可手动指定已安装 dsh 的 `lib/bin.js` 路径。脚本回收自己的测试进程、配对凭证与目录。[真实宿主验收脚本](../../scripts/acceptance-dsh-reminder.mjs)

## 授权和故障回归

- 旧简报、表达、个人助手与安装身份均不能代替独立 `reminder_create` 凭证。新权限只允许创建提醒及核对自身身份。管理端按 scope 和名称撤销，即使丢失配对文件也能办理。读取请求体期间被撤销的凭证在写入前失效。[Runtime HTTP 测试](../../packages/runtime/tests/agent-reminders.test.ts)
- SDK、CLI 子进程和 MCP 子进程并发提交同一意图，均返回原回执。重启、时钟改变、本人修改或删除提醒后，原请求不会重新建单。同 ID 改参数返回 409。每个身份每 UTC 整点小时最多新建 30 条；重放、失败事务、回拨和不同调用方分别验证。[跨入口测试](../../packages/cli/tests/reminder-integration.test.ts)
- 原有简报的 dsh 验收在提取共用测试工具后重新跑通。新提醒配置与简报配置可以分别加载；插件打包清单包含提醒示例。[dsh 配置说明](../../apps/dsh-plugin/README.md#让-dsh-安排一次提醒)
- 临时 Runtime 的真实回环 HTTP 压测中，同一身份并发提交 64 份相同请求，全部返回相同回执且只保存 1 条。随后并发提交 40 个新 ID，当小时剩余 29 条配额全部用完，另 11 条返回 429。达到配额后原请求仍可取回首次回执。
- 全仓构建、类型检查和按包串行测试通过，共 671 项通过、3 项条件跳过。真实 Windows 通知另由本轮 dsh 验收脚本覆盖。
