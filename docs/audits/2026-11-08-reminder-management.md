# 提醒查看确认、失败重试与恢复回归（2026-11-08）

关联 [#61](https://github.com/destinyTaoTao/maneki-pet/issues/61)、原始提醒票据 #22 / #23。基线 `main@93db92c`，设计先行提交 `e2b99fa`。本轮继续补齐近期 dsh 个人助理，不开放工程派发或第二宿主，已保留的人工授权/真实设备项不变。

## 结果与使用

- `/maneki assistant` → 提醒：accepted / failed 项可点“我已查看”，持久记录 UTC 查看时间并在清单显示。打开面板、OS 受理与通知展示都不自动确认；原系统状态与失败原因仍保留，也不完成关联待办。个人助手跨 profile 共享同一查看状态。
- failed 项可点“重试系统通知”。这是一项显式新尝试，恢复 pending、清除旧错误/查看标记/通知批次，保留原定时间、时区、内容与累计 attempts。关联待办已完成或不存在时拒绝；pending / sending / accepted / cancelled 不重投。勿扰、通知预算继续生效，不自动重试失败项或反复催促。
- 两操作复用现有 assistant scope 的 mutations 事务，要求当前 id/version 与 clientRequestId；同请求重发不重复办理、同请求换参数拒绝，不同客户端竞争只有一个可推进版本。表达凭证、模型回复和 MCP 输出不能授权这些变更。接口只接受动作所需字段，不能顺带更改内容或时间。
- 记录存储或完成记账失败后，调度至少退避 30 秒再自动扫描，重复 wake 不绕过退避。正常到期继续按最近时间唤醒；系统时间变化/暂停恢复由既有最多 30 秒扫描补捞，未增加 OS 监听器或改变系统时钟。
- 发送后、完成记账前异常会保留 sending，结果待核实，不改成 failed 或发新批次；重启时恢复为 pending 并复用原批次。外部 OS 通知仍可能重投，不承诺严格一次。持久存储不可用时需恢复存储并重启对账，不能靠手动重试制造第二份未知尝试。
- 同步修正全局云端开关文案为“允许 Maneki 自身云端调用（对话 / 语音）”，与已有实际授权范围一致；未改动用户真实设置或进行云端调用。

## 验证边界

新增 Runtime 提醒管理与恢复回归 8 项、桌面面板回归 1 项：

1. 正式 HTTP 路由的跨客户端状态共享、同 ID 幂等、版本冲突、express 拒绝；重启后查看时间和原失败状态保留。
2. 显式重试保留原时间/累计次数、清除旧标记/批次；勿扰期间停留 pending，恢复后只推进一个尝试。
3. 额外参数、已完成关联待办、未失败或在途状态拒绝；事务失败不留查看标记或幂等假成功。
4. 两个个人客户端同时重试，同版本仅一方成功。
5. SQLite v5→v6 备份；迁移中在 DDL 后注入错误，确认事务回滚、停止启动，恢复后消息、语音配置与旧通知批次保留。
6. 持续存储错误不形成 1 ms 空转，wake 洪泛不绕过 30 秒退避；存储恢复后正常投递。
7. 模拟发送后记账失败及恢复，复用旧批次，新增到期项另批发送；没有以新 ID 重试未知结果。
8. 虚拟时钟后跳不提前投递、前跳与暂停恢复扫描补捞、accepted 不自动再投。该测试不改变真实 OS 时钟，不等于真机休眠验收。
9. 面板打开不自动确认；“已查看”与系统受理同时显示，按钮只提交目标项和版本。

全仓 `pnpm -r build`、`pnpm -r test`、`pnpm -r typecheck` 均通过；351 项测试通过、2 项设备测试默认跳过（Core 96、Runtime 126、Desktop 83、dsh 插件 7、dsh Adapter 22、platform-core 8、B站 5、CLI 4）。测试使用隔离临时目录/数据库及通知替身，未向用户发实际测试通知，没有操作安全授权按钮。

`pnpm --filter @maneki-pet/desktop tauri build --no-bundle` 通过，生成 Windows release 桌面与 Runtime bundle；未打安装器、未替换用户安装程序。Rust 源码本轮未修改。

## 迁移与剩余项

SQLite v5→v6 前生成 `runtime.db.bak-5`（更早库按源版本备份），事务增加 nullable seen_at 列，旧记录默认 null。桌面/Runtime 一起更新；旧 Runtime 拒绝 v6，回退须先停止后台并显式恢复对应备份，恢复旧备份会丢失其后的修改。此前云端语音配置及密钥引用保持原值。

仍保留：真实休眠/恢复/时钟变化、通知可见性与 OS 重投表现、正常负载通知调用 p95、长期资源、安装器升级/卸载、原生配对/退出确认、云端账号计费与音频设备、macOS/Linux。未更新已安装应用或真实用户数据库；不以本轮局部验证勾选 M1/M2/M3/M4 整体出口。

## 2026-11-22 · 单次提醒调度延迟样本（#23）

Windows 11 build 26200、i5-13600K、Node 24.12.0。启动隔离 Runtime，经正式 HTTP 创建 24 条单次提醒，到期时刻相隔 300 ms。使用真实墙钟、真实定时器、默认通知预算和本地 SQLite。每条仅调用一次接入的通知器，均未早于到期时刻。到期至通知器入口的延迟为最小 21 ms、p95 71 ms、最大 72 ms。

运行 `corepack pnpm -r build` 后执行 `node scripts/acceptance-reminder-timing.mjs` 可复验。该脚本在通知器入口采样并返回合成受理结果。Windows 通知命令执行、系统横幅、真实睡眠恢复及桌宠和 dsh 同时工作的负载仍各自验收。[复验脚本](../../scripts/acceptance-reminder-timing.mjs)
