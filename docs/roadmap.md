## 依赖与发布原则

```text
M0 → M1 → M2（共享 Runtime、dsh 基础插件与管理入口）
             ├→ M3 文字主会话 + M4 个人待办/单次可靠提醒
             │                 → M3 按键语音集成（近期个人助理出口）
             └→ M2b 工程派发/原生审批/完整恢复（个人助理后续独立验收）
                    → M5 / M6（其他宿主与扩展暂缓）
```

M3 与 M4 在各自所需的 M2 生命周期、鉴权、配置、存储与通知出口通过后推进，不以 dsh 新会话/原生审批/完整恢复或外挂记忆 spike 为前提。先完成文字主会话、个人待办与提醒，再接入语音；M4 的结构化文字入口和调度不依赖模型/语音。M2b 的安全与恢复 gate 仍是开放工程执行的必要条件，后置不等于放宽。M5/M6 保留远期范围，近期不新增第二宿主或通用插件框架。

- 先发布 Windows 已验证基线；macOS/Linux 是目标平台，分别记录通过、受限或未验证，不以 Windows 验收替代。
- 各能力通过其相关的 Windows 前置出口后进入下一步；工程派发专属 gate 不阻塞非执行助理能力，M1/M2 整阶段缺口仍保留。平台矩阵单独跟踪，macOS/Linux 未验证时不阻塞 Windows 开发/发布，也不能勾选已支持。
- 每阶段只开放已验证能力。harness 接入不满足审批要求时仅观察，不为了通过里程碑而绕过安全策略。
- 所有代码阶段运行 `pnpm -r build && pnpm -r test`；再按下列场景做最小集成/设备验证。只有文档时检查一致性、链接与契约示例，不宣称运行通过。
- 架构与 Interface 调整先同步 [architecture.md](./architecture.md)，设计提交与实现分开。首个可用版本不以第三方技能、市场或多宠为门槛。
